1. Project Overview

The Employee Leave Management System is a full-stack web application that allows employees to apply for leave, and managers/admins to review, approve, or reject those requests. It tracks leave balances per employee, per leave type, per year — and automatically deducts days when leave is approved.

Who it's for:

RoleWhat they can do
EmployeeView leave balances, submit leave requests, cancel own requests
ManagerAll employee actions + view/approve/reject team requests, team calendar, team balances
AdminFull access — all requests, all users, all balances system-wide

4. Running the Backend

Option A — In-Memory Database (Quickest)

No database installation required. Data is seeded automatically on startup.

# From the project root
cd backend\LeaveManagement.Api

dotnet run --UseInMemoryDatabase=true --urls "http://localhost:5000"
The API will be available at http://localhost:5000
Swagger UI (interactive API docs) at http://localhost:5000/swagger

Option B — SQL Server

Edit backend\LeaveManagement.Api\appsettings.json and update the connection string:

"ConnectionStrings": {
  "DefaultConnection": "Server=YOUR_SERVER;Database=LeaveManagementDb;Trusted_Connection=True;TrustServerCertificate=True"
}

Then run normally:

cd backend\LeaveManagement.Api
dotnet run --urls "http://localhost:5000"

The database and tables are created automatically on first run via EnsureCreatedAsync(), and seed data is inserted if the database is empty.

Verifying the Backend is Running

Open your browser and go to http://localhost:5000/swagger — you should see the Swagger UI with all API endpoints listed.

5. Running the Frontend

# From the project root
cd frontend\leave-management-ui

# Install dependencies (first time only)
npm install

# Start the dev server
npm start
The Angular app runs at http://localhost:4200
It communicates with the backend API at http://localhost:5000
⚠️ Start order matters: Always start the backend first, then the frontend. The Angular app needs the API to be running to log in and fetch data.

7. How to Use the Application

As an Employee

1
Log inGo to http://localhost:4200, enter your email and password (e.g. employee@company.com / Password123!)
2
View your leave balancesThe Employee Dashboard shows how many days you have remaining for each leave type this year.
3
Submit a leave requestChoose a leave type, pick start and end dates, provide a reason, and submit. The system automatically calculates working days (weekends excluded) and checks your balance.
4
Track your requestsAll your requests are listed with their current status: Pending, Approved, Rejected, or Cancelled.
5
Cancel a requestYou can cancel your own Pending or Approved requests. If an approved request is cancelled, your leave balance is automatically restored.

As a Manager

1
Log in as managerUse manager@company.com / Password123!
2
View team leave requestsThe Manager Dashboard shows all pending and historical requests from your direct reports.
3
Approve or Reject requestsClick Approve or Reject on any Pending request. You can optionally add a comment for the employee. Approving deducts days from the employee's balance.
4
View team balances & calendarSee each team member's remaining leave days, and a calendar view of all upcoming approved/pending leave across the team.

Business Rules to Know

  • Overlapping leave requests (Pending or Approved) are not allowed for the same employee.
  • Requests covering only weekends are rejected (0 working days).
  • You cannot request more days than your remaining balance.
  • Only the employee's direct manager (or an Admin) can approve/reject their requests.
  • Cancelling an already-approved request restores the balance.

9. Key Classes to Understand

Entities (Core Data Models)

Entity User backend/LeaveManagement.Core/Entities/User.cs

Represents any person in the system. Supports a self-referencing hierarchy — a User has a ManagerId pointing to another User, and a collection of DirectReports.

Key properties: Id, Name, Email, PasswordHash, Role (Employee / Manager / Admin), DepartmentId, ManagerId, IsActive

Entity LeaveRequest backend/LeaveManagement.Core/Entities/LeaveRequest.cs

Records a single leave application from an employee. Tracks who applied, what type of leave, date range, working days calculated, current status, and the manager's decision.

Key properties: UserId, LeaveTypeId, StartDate, EndDate, DaysRequested, Reason, Status, DecidedById, ManagerComment

Entity LeaveBalance backend/LeaveManagement.Core/Entities/LeaveBalance.cs

Tracks how many leave days an employee has per leave type per year. The computed property RemainingDays = TotalDays - UsedDays drives all balance validation. Balances are auto-created per year when first accessed.

Key properties: UserId, LeaveTypeId, Year, TotalDays, UsedDays, RemainingDays

Services (Business Logic)

Service LeaveService backend/LeaveManagement.Infrastructure/Services/LeaveService.cs

The heart of the application. Contains all leave-related business logic. This is the most important class to understand.

  • CreateLeaveRequestAsync() — validates dates, checks for overlaps, verifies balance, calculates working days, creates the request
  • ApproveLeaveRequestAsync() — validates manager authority, checks balance, deducts used days, updates status
  • RejectLeaveRequestAsync() — validates manager authority, sets status to Rejected (no balance change)
  • CancelLeaveRequestAsync() — cancels request; if it was Approved, restores the balance
  • CalculateWorkingDays() — counts Mon–Fri days between two dates (weekends excluded)
  • EnsureUserBalancesForYearAsync() — auto-provisions balance records if they don't exist yet for a year
  • GetTeamCalendarAsync() — returns Approved/Pending leaves for a manager's team in a date window
Service AuthService backend/LeaveManagement.Infrastructure/Services/AuthService.cs

Handles all identity operations: user registration (with BCrypt password hashing), login, JWT token issuance, refresh token management, and profile retrieval.

  • RegisterAsync() — hashes password with BCrypt, creates user, issues JWT
  • LoginAsync() — verifies credentials, issues JWT + refresh token
  • RefreshTokenAsync() — validates a refresh token and issues a new JWT pair
  • RevokeTokenAsync() — marks a refresh token as used (logout)
Service JwtTokenGenerator backend/LeaveManagement.Infrastructure/Services/JwtTokenGenerator.cs

Generates signed JWT access tokens (60 min expiry) and random refresh tokens (7 day expiry). The JWT encodes the user's Id, Email, and Role as claims, which controllers read to authorize actions.

Infrastructure

Data AppDbContext backend/LeaveManagement.Infrastructure/Data/AppDbContext.cs

The Entity Framework Core database context. Defines all DbSet tables: Users, Departments, LeaveTypes, LeaveBalances, LeaveRequests, RefreshTokens. Supports both SQL Server and In-Memory modes.

Data DbInitializer backend/LeaveManagement.Infrastructure/Data/DbInitializer.cs

Seeds the database on startup with departments, leave types, users (admin + manager + 3 employees), leave balances for the current year, and sample leave requests. Only runs if the tables are empty.

API Controllers

Controller LeaveRequestsController backend/LeaveManagement.Api/Controllers/LeaveRequestsController.cs

Exposes all leave request operations as HTTP endpoints. Reads the logged-in user's ID from JWT claims (ClaimTypes.NameIdentifier) on every request. Role-based authorization is enforced at the action level using [Authorize(Roles="Manager,Admin")].

Frontend

Angular auth.interceptor.ts frontend/src/app/core/interceptors/auth.interceptor.ts

An Angular HTTP interceptor that automatically attaches the stored JWT token as an Authorization: Bearer ... header to every outgoing API request. This means you don't need to manually add the token in each service call.

Angular auth.guard.ts frontend/src/app/core/guards/auth.guard.ts

Route guards that protect pages. authGuard redirects unauthenticated users to /login. managerGuard restricts the /manager route to users with the Manager or Admin role only.
